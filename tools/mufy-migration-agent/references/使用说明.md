# 迁移 Agent 使用说明

## 这套包是什么

把它交给有浏览器操作能力的 Codex 使用。Codex 负责打开来源和测试站、对比、修复与实际复验；包里的工具负责转换、分工、版本和证据检查。它不是双击就能后台搬完所有卡的独立程序。

当前为候选版，只允许单卡试运行，不允许多人批量迁移。`doctor` 的 `ok:true` 表示文件完整；`distributedReady:false` 表示尚未通过多人批量认证。旧 1.0.0 已撤回推荐。

## 接收者需要拿到什么

1. 同一个完整代码包，不能只拿 SKILL.md，也不能用旧版混着执行。
2. 协调者分配的一份 job：名单、版本指纹、assignment，以及这一张卡的授权本地档案。代码包不包含真实卡原文。
3. 自己的 Codex 浏览器工具，以及 Mufy 和 8091 测试站的正常登录。不要复制别人的登录信息。
4. 本机已安装 Bun。工具用 `bun --version` 检查；转换及运行依赖已打包，执行时不需要安装整个平台或运行 bun install。

如果还没有 job、授权档案或浏览器能力，先补齐这些条件，不能自行猜一张卡开始导入。

## 如何启动

解压后，以整个包目录作为 Codex 工作目录。也可以把完整目录安装到本机 `~/.codex/skills/mufy-migration-agent/`；已有同名版本先核对，不覆盖进行中的任务。

先在包目录执行：

```powershell
bun dist/agent.mjs doctor
```

检查版本和 packageId 与协调者发来的一致。输出 PACKAGE_DRIFT 等错误说明包被改动，应重新取得同一版本，不要自行改 release.json 或删掉校验。

把下面这段话连同 job 位置交给 Codex：

> 使用这个目录里的 mufy-migration-agent 技能。先读 SKILL.md 和 references/使用说明.md，运行 doctor，核对我提供的 job、执行者ID和分配卡号，只处理分配项。使用正常浏览器公开来源与授权本地档案，在8091正常网页迁移或修复。已有目标就不重复导入。先保存失败证据，再自行定位、修复和真实复验；有未解决项不能报通过。完成后交回逐卡结果、证据和分开记录的计算/浏览器耗时。不要发布共享渲染器、不要访问数据库或读取登录凭据。

这里的 job 位置、执行者ID、卡号由协调者给出，不能凭示例填写。

## 协调者先做的事

以一个新的工作目录创建 job。`roster.json` 格式见 operator.md，必须使用实际核实的本地 sourceKey、姓名和来源链接。当前版本仅允许一张 pending/imported 项；held 项保留具体原因。已经导入的卡设 imported 并填已有聊天地址。

运行指纹来自协调者确认的测试站发布记录或正常公开版本标记；拿不到就保持待确认，不能随便写64位数字。它是代码版本指纹，不是登录信息。

```powershell
bun dist/agent.mjs init --roster "D:\MigrationJobs\canary-roster.json" --out "D:\MigrationJobs\canary-job" --runtime "协调者确认的64位SHA256"
bun dist/agent.mjs assign --job "D:\MigrationJobs\canary-job" --workers worker_a
```

上面是路径格式示例，不是已经为接收者创建好的任务。代码包保持只读，job 放在包外。分发给执行者的私有档案仅限分配范围。

## 执行者实际流程

1. 核对分配后 `claim --job 完整job路径 --worker worker_a --rank 实际卡号`。重复领取失败时先检查现有记录，不删除别人的 claim。
2. 运行 `scaffold`，参数同 claim，生成19项 blocked 的验收模板。模板不是证据，也不代表已验收。
3. 正常打开来源，核对姓名、正文和全部组件。保存完整公开组件、样式、头像开关、渲染规则与采集证明。大组件分段读取并核对完整长度；没有采集到不等于来源没有。
4. 按 operator.md 准备 detail、rules、appearance、source-proof、授权 prompt 和 input.json。已有目标跳过 prepare/import，直接对照现有卡。
5. 对未导入卡运行 `prepare --job … --worker … --rank … --input inputs/卡号/input.json`。输出仅是本地待导入XML。报错先修输入或转换问题，不能跳过规则或删掉内容来凑成功。
6. 在8091正常导入界面上传该XML一次。确认实际角色及目标聊天地址后运行 `receipt --job … --worker … --rank … --url 实际8091聊天地址`。上传超时后先查实际结果，不能盲目再导入。
7. 对照来源做开场、至少两条真实回复、手机与桌面、状态栏折叠、流式稳定、侧边固定组件、头像、姓名、媒体和自定义交互。源站没有的功能也需实际观察依据，不能全部填“不适用”。
8. 有问题先留证，按 repair.md 自行定位、最小修复、跑有关回归并实际复验。内置 repair 仅有播放器盒模型配方，其他问题由 Codex 修代码或正常 owner UI 修复；不能把没修好的项直接交用户返工。共享渲染器问题交协调者统一处理。
9. 完成自己的实际报告后运行 `review --job … --worker … --rank … --report workers/worker_a/卡号/card-report.json`。未通过会返回具体缺项；修复后重新提交新工作报告。不要把原模板改成全通过来消除报错。
10. 协调者收齐证据和报告，重新确认当前运行指纹，再运行 `merge --job … --runtime 当前实际指纹`。检查 held、pending、passed 明细；不能只看退出码。全部实际通过才交用户审阅。

## 什么叫完成

导入成功、按钮能点、截图里看起来相似、工具校验通过，都不能单独代表整卡完成。19项和来源组件清单都必须有实际结论；所有未解决项清零。已知不能访问的媒体、名字未绑定、动画没验证、回复格式缺失，都要明确保留，不能为了收尾虚构通过。

旧回复可以复用，但必须在当前运行版本实际检查；未看过的旧截图不能直接移作本次通过证据。流式稳定需要实际生成过程记录，历史最终回复不能证明过程没闪烁。

## 多人怎么配合

候选版先由一人跑单卡，暂不分发批量任务。通过真实单卡及交接验收后，由协调者发布新的、已认证代码版本再分工。每个人使用同一 packageId、唯一卡号范围和自己的浏览器窗口；共享发布只有协调者一个入口。跨机器的 claim 文件不是分布式锁，防重依据是唯一分配及权威导入登记。

## 遇到问题怎么处理

| 情况 | 处理 |
| --- | --- |
| 需要登录 | 用户正常登录，不读或搬运凭据；继续可独立进行的本地工作 |
| 502/429/页面不可用 | 保存真实页面、时间和具体环节；不重复提交、不据工具超时猜测封号 |
| 来源更新或链接变化 | 记录原链接与变化，重新核对身份，不猜替代链接 |
| prepare失败 | 保留原件，定位具体缺失字段、规则或组件；不能删除内容凑通过 |
| review失败 | 看错误队列，修复并实际复验；没有证据仍为未通过 |
| 发布版本变化 | 协调者创建保留旧证据的新版本任务，对受影响项重验；不改旧证据哈希 |
| 用户等待或调度间隔 | 单独记录，不算Agent净工时；拿不到准确总量就明确未知 |

执行者交回：packageId、assignment、卡号/目标地址、导入登记、逐卡报告、原始公开证据、修复前后记录、具体未解决项及耗时记录。不要把账号信息或授权私有原文发进公共交接包。
