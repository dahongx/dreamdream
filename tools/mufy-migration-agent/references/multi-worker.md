# 多人协作交接

协调者只做一次 init、一次 assign。将同一个不可变包、只读 roster/job/assignments、各自授权输入发给执行者；执行者只领自己的 ranks。每个人可在自己的机器/工作副本操作浏览器，不能共用同一可控浏览器窗口抢焦点。

共享文件夹使用 claim 的独占创建避免重复；跨机器副本的claim不是分布式锁，真正的防重复依据是协调者唯一分配、冻结名单和导入receipt总表。协调者不得给两人发同一rank；要转交先核对实际TEST是否已导入和未保存修改，再调整新批次分工，不靠复制新job绕过旧receipt。

源同一线上角色可对应多个本地档案，保持本地行不合并，分配给同一执行者避免重复采集。先前已对应名单、作者、收藏、点赞和来源链接保留在协调者原表；热度注明10月13日快照，不能伪称实时。包不包含原始人物私有档案，按各自rank最小化提供授权本地材料。

执行者返回 workers/自己的子目录、使用到的证据、claim、receipt和待验报告；不覆盖其他worker或协调者目录。协调者在权威job中核对packageId/rosterSha256、重复rank/来源/实际目标，再使用 review、merge重新验证文件，而不是接受对方一句“好了”。发现同一rank报告冲突或不同runtime指纹，保持未通过，先解决冲突。

共享渲染器修复与发布只有协调者一个入口。所有个人卡先完成约定的批次预构建检查，再由协调者合并提案、跑相关回归、确认精确基线和授权后统一发布，随后重验受影响项。不要让每个执行者各部署一份，导致前面的修复回退。

依赖外部媒体或当前工具的真实缺口留具体原因。held与failed/pending不能混入passed；只有范围内全部实际验收通过再提交用户人工复核。不能保证任意作者脚本都能无需修改自动通过。
