# 产品思考 —— 账号注销

> 技术交接见 [docs/handover/account-deletion.md](../handover/account-deletion.md)。

## 起点是一个被推翻的设计

最初的想法是「注销账号，但聊天记录留在库里」——这些日志是平台唯一真正积累的东西，
删了可惜。方案也想清楚了：把 users 行变成一个没有任何身份字段的墓碑，内容挂在它下面。

推翻它的不是工程量，是**已经发布出去的那份协议**。使用者協議 4.6 条列了三项例外，
第三项写的是「已被不可逆匿名化、无法再与你关联的数据」。也就是说保留合规的前提是
**真的做到不可逆去标识化** —— 邮箱要从 GoTrue 的 `auth.users` 和 `auth.identities` 里
彻底抹掉，否则那堆日志随时能重新关联回人，例外条款当场失效。

一旦把这条讲清楚，「保留」方案的成本就暴露了：它要碰 GoTrue 内部表、要维护一套墓碑
渲染、要在全站八个展示点兜底「已注销用户」，换来的是一份法律上永远站在悬崖边的数据。
而「全删」在这个库里几乎是免费的 —— 0011 那条 `ON DELETE CASCADE` 早就把路铺好了。

**教训：先去读自己发布过的东西，再设计。** 那份协议是半年前写的，写的时候没人想到
它会反过来决定一个功能的形状。

## 真正难的不是删自己的数据，是不删别人的

「把他所有的数据都删了」听起来干净利落，但级联链会顺手做一件没人要求的事：
创作者的角色卡被删 → `chat_sessions.character_id` 的 CASCADE 触发 → **其他用户**跟这些
卡的全部对话和消息一起消失。

这不是删他的数据，是删别人的数据，而且对方毫无感知。讽刺的是，这恰好是最初那个
「聊天记录要留着」的诉求 —— 只不过换成了别人的聊天记录。

所以最后的形态是：注销者本人的一切硬删，第三方的会话**断链保留**。角色行没了，会话
和消息还在，在列表里以灰条呈现。用户知道记录还在、只是聊不下去了，而不是某天发现
一段对话凭空蒸发。

顺带发现：仓库里早就有这套灰条 UI —— 「角色被作者改成私密」用的就是它。新增的
「创作者已注销」只是给同一个闸多加了一种成因，改一行判据、换一句文案。**没有为它
新造一套东西，是这次改动里最省的一笔。**

## 三个不能两全的地方

**冷静期。** 主流做法是 7 天可撤销。没做，因为用户的原话是「很急需」——急需注销功能
的人，通常不需要被挽留七天。代价是误触不可逆，靠密码复核 + 六条后果清单 + 明确勾选
来挡。

**交易记录。** 「全删」在这里必须让步：日本帐簿书类有保存义务，隐私政策 8.2 也自己
写了这条。所以订单不删，只是脱钩成没有主人的记录。这不是妥协，是**「全删」这个词
本来就不该包含法定保存义务**。

**邮箱指纹。** 注销后邮箱释放、可以重新注册，这是对用户友好的。但新账号的
100 金 / 200 银来自列默认值，「注销 → 重注册」可以无限刷 —— 对一个已经在真收钱的
平台，这是实打实的口子。留一份加 pepper 的单向指纹是唯一残留物，代价是「删得干净」
这句话要打一个星号，所以它必须写进隐私政策，而不是当成实现细节藏起来。

指纹表刻意做成两列、不含 user_id、不关联任何内容 —— 这不是洁癖。一旦它能指回内容行，
那些内容就重新变得可关联，整个「注销即删干净」的说法就崩了。

## 一个反直觉的判断

「保留数据」看起来是更保守、更安全的选择，实际上它需要更多的辩护、更多的代码、
更多说不清的边界。**硬删除才是那个不需要解释的方案。**

留下来的东西越少，能出问题的地方越少。这次唯一留下的两样（脱钩的订单、无主的邮箱
指纹），都是因为不留会出更大的问题 —— 而不是因为留着有价值。
