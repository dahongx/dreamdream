# 防回退不能靠“记得保留”

实现说明见 [handover](../handover/mufy-candidate-baseline.md)。

迁移会经历多次局部修复。候选即使自身功能正确，只要从较早快照生成，也会在下一次覆盖时悄悄带走上次修复。rank46 就出现了这个风险：旧候选不含现站后来增加的 84 行样式，尚未发布便被新基线核对拦住。

把“当前内容→改动一→改动二→最终产物”建立成可验证的哈希链，比在每个脚本里凭记忆挑文件可靠。保护对象是用户当前内容，不是最早导入包。逐阶段检查也不能替代真实 UI、自查修复和媒体确认；16 组链通过只说明没有从过期版本出发，不能改称16张验收完成。

自动化本身也会误读：弹窗还没打开时旁边的创作输入框可能为空，滚动胶片的第一个 DOM 副本可能已被裁掉。必须验证实际界面和控件身份，保留误读及纠正证据，不能把工具误点包装成网站丢数据，也不能用虚假成功掩盖它。

门禁覆盖面也需要审计。初轮16组没有包括两个较早生成的局部候选，后续已补足到18组。不能因为“已检查的全通过”就默认未纳入检查的也通过；必须对照实际待发布清单逐项补齐，当前基线守卫仍只是一道门禁，不是最终验收。
