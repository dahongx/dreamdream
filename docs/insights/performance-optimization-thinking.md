# 性能优化的产品思考

## 问题的本质

首页慢不是技术细节问题，是**产品信任问题**。用户看到空白页 2-3 秒，会怀疑：
- 网站挂了？
- 我的网络有问题？
- 这个产品靠谱吗？

对于一个「creator 友好」定位的平台，慢速加载会直接流失潜在创作者。

## 为什么会慢？

**技术债的累积：**
1. 早期为了快速上线，所有页面都用 `force-dynamic`（最简单的方案）
2. 数据库索引按需添加，探索页的查询模式（nsfw + tags + 热门排序）没有对应索引
3. 连接池设置保守（3 个连接），适合单用户测试，不适合多用户访问

**没有及时发现：**
- 本地开发时数据量少，查询很快
- 单用户测试时连接池够用
- 慢速问题在有一定数据量 + 并发访问时才暴露

## 优化的权衡

### 我们选择的路径：数据库层优化

**为什么不用缓存？**
- Redis 缓存需要额外基础设施
- 缓存失效策略复杂（角色更新、删除、新增都要考虑）
- 缓存一致性问题（owner 修改角色后，列表要多久能看到？）

**为什么不改渲染策略？**
- 角色详情页和聊天页依赖动态 CSS/正则渲染
- 如果用静态生成或长时间 ISR，owner 修改后要等待才能看到效果
- 这会破坏「creator 友好」的核心体验

**为什么选择索引 + 连接池？**
- 索引是数据库原生能力，无额外复杂度
- 查询从 2000ms 降到 50ms，效果立竿见影
- 不影响任何业务逻辑和渲染策略
- 写入成本可以接受（创作者发布角色 << 访客浏览角色）

### 没有解决的问题

**字体加载仍需优化**
- 4 个 Google Fonts，10 个字体变体文件
- 首次访问需要下载 ~100-200KB 字体
- 但这是设计系统的基础（DESIGN.md），不能轻易移除

**可能的方案：**
- 字体子集化（只包含常用汉字）
- Variable fonts（减少变体数量）
- 需要设计师确认是否影响视觉效果

## 未来的优化空间

### 短期（如果索引效果不够）
1. **探索页局部缓存** - 默认推荐列表缓存 1-5 分钟
2. **全文搜索索引** - 如果按名称/简介搜索慢，添加 pg_trgm

### 中期（产品成熟后）
1. **CDN 缓存** - 公开角色的静态资源（封面图、头像）
2. **图片优化** - WebP 格式 + 响应式尺寸
3. **服务端组件拆分** - 用 Suspense 让部分内容先渲染

### 长期（规模化后）
1. **读写分离** - 探索页查询走只读副本
2. **Redis 缓存层** - 热门角色列表、用户会话
3. **边缘计算** - Vercel Edge Functions / Cloudflare Workers

## 产品决策的启示

**性能是特性，不是技术指标**
- 慢 = 不专业 = 流失用户
- 快 = 可靠 = 用户信任

**优化要尊重产品定位**
- 我们是「creator 友好」，不是「访客优先」
- 所以选择数据库优化（不影响 creator 体验），而不是激进缓存（可能延迟 creator 修改的可见性）

**技术债要主动管理**
- `force-dynamic` 适合 MVP，不适合产品化
- 索引应该在设计数据模型时规划，不是事后补救
- 性能监控应该从第一天开始，不是用户投诉后

## Takeaway

这次优化本质上是**还债**：
- 还早期快速上线欠下的技术债
- 还没有提前规划查询模式欠下的设计债
- 还没有及时监控性能欠下的运维债

下次设计新功能时，应该问：
1. 这个查询会有多少数据？需要什么索引？
2. 这个页面的渲染策略是什么？能缓存吗？
3. 这个功能上线后，怎么知道它是否变慢？

性能不是优化出来的，是设计出来的。
