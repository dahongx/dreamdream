# 复制行为不能用另一个动作代替

谢闽面具表单再次证明“提取后聊天框出现了文本”不等于功能正确。面具是供玩家另行使用的人设资料，不应被迁移器偷偷放进对话草稿。新的验收既核对正文也核对末尾注释、空字段默认值和空格处理，复制成功只由宿主实际写入确认；原站的假成功和旧候选的错误语义均保留，不用改历史记录制造一致。

修复不能只停在当前渲染器。旧迁移暂存流程会把clipboard写入统一替换为填草稿，因此新一批仍可能重复同一错误。现在对四种已核实的公开复制组件，在暂存入口就保留原语义，并让旧头像转换默认硬失败。历史候选不重写，运行时向后兼容与未来迁移防回退分开验证。

实现与边界：[handover](../handover/mufy-oc-profile-copy.md)。

这次发现两种“看起来成功”：按钮无反馈地永久等待，以及浏览器 execCommand 返回 true 却没有写入系统剪贴板。验收必须实际粘贴已知合成内容比对，而不是看返回值或成功提示。

档案表单原意是让玩家把自拟人设复制到面具。将其变成聊天草稿会改变用户流程甚至误发人设，因此此次保留真正剪贴板语义。只把这个已知表单的写入交给现有宿主复制工具，用户手势、窗口来源和长度均受约束；不为角色脚本开放读取剪贴板或宿主数据的能力。

失败时明确提示手动选择复制，清空不残留成功提示。作者原有样式、字段、输出内容与七区折叠保持不变。正常源站缺陷（例如原站与 TEST 同时发生的粤语切换角色名丢失）另行注明，不借迁移擅自改文案。
# 开场复制也必须实测

公开指令卡也需要区分“原始模板”“平台绑定后的可复制值”“剪贴板实际值”。简行舟首轮把两处正常角色绑定当成复制差异，随后用渲染data-command以及唯一允许的占位符替换双重核验确认；原始模板仍不相等，不能抹去这一事实。与此同时手机内层10px溢出是真问题，单独修根盒模型，不用内容差异解释布局问题。

同一公开头像库存在大小写/拆分标题和不同 alert 文案变体：用已观测的完整组件签名做兼容，而不是将一张卡修好就推定所有复制按钮正常。邱石15张原图的逐项复制证据补齐了这一盲点；过渡期首次未命中也保留，不把旧剪贴板值算成功。

头像库同样适用：用户要的是图片链接进入剪贴板，不是出现在聊天框。此次通过33张实际点击复制、真实粘贴和空草稿/零发送核验纠正历史候选的语义偏差。旧候选审计历史保留，但兼容运行时优先截获为原始复制动作，不通过扩权恢复alert。不要把“按钮有响应”当作验收通过。

相同的“复制”外观不代表语义相同：公开开场需要进剪贴板，不应偷偷变成聊天草稿，更不能自动发送。此次用各自独立的合成标记验证，避免把来源先写进剪贴板的内容当成 TEST 复制成功。宿主只接管已知两种公开组件的写入；不开放作者的通用剪贴板对象。详见 [handover](../handover/mufy-oc-profile-copy.md)。
