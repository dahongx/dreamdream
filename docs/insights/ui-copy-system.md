# 产品思考 — 为什么 UI 不该替开发者做自我介绍

> 技术交接见 [handover/ui-copy-system.md](../handover/ui-copy-system.md)。

## 问题不只是句子长

旧文案经常从实现出发：平台用了什么协议、一个字段如何进入 prompt、组件运行在哪种 sandbox、
数据是否留档。它们多数没有说错，却要求用户先理解产品内部模型，才能完成眼前的动作。

另一类问题来自页面结构。eyebrow、H1、副标题、卡片标题和空状态连续解释同一件事，单句看都
合理，叠在一起就像说明书。用户会先看到产品在解释自己，真正的操作反而退到后面。

## 这次采用的判断顺序

看到一条辅助文案时，依次问：

1. 删掉后，用户还能完成任务吗？能就删除。
2. 它是否在说明不可逆后果、费用、权限或错误恢复？是就保留并写准确。
3. 它是否只对专业创作者有用？是就放到对应字段或技术详情，不常驻在页头。
4. 它是否在讲实现，而用户真正关心的是结果？改写成结果。

这套顺序比逐句“润色”更稳定。润色很容易把一段没必要存在的话改得更漂亮，却没有降低阅读负担。

## 不同受众需要不同密度

玩家只需要角色、聊天、余额和下一步。创作者需要知道格式约束，但不必理解 host、RSC payload
或数据库关系。管理员和开发者本来就在诊断系统，token、latency、模型成本等术语对他们是有效信息。

所以目标不是全站都写得口语化，也不是把专业词清零，而是让信息出现在正确权限、正确页面和正确
时机。正则捕获组留在高级编辑器很合理；把 Supabase Storage 写进头像报错就不合理。

## 几个代表性取舍

- 登录页删除“不审核内容”的伪同意条款，但平台零审核立场没有改变。产品立场不该伪装成用户协议。
- NSFW 开关只说明显示或隐藏 R18 内容。治理方式属于规则说明，不属于按钮 tooltip。
- 聊天仍提示回复生成失败并提供恢复动作，但不告诉玩家是哪家供应商的安全策略触发。
- 角色简介帮助保留“会公开展示”，删除 `sales pitch` 和 prompt 资产的内部解释。
- Studio 保留正则、捕获组和替换语法，把 `Proposal`、`pack.globalCss`、`mock 数据` 等实现名换成
  “加入草稿”“替换当前皮肤”“示例内容”。
- 删除确认不能为了少字而模糊。文案越精简，越要把永久损失写完整。

## 页面应该留下什么感觉

寄情不是后台管理系统。大号衬线标题、暗夜书架的氛围和少量有性格的措辞应该保留；真正要删的是
重复解释、营销套话和开发过程的痕迹。少字不是目的，让用户直接进入角色、故事和创作才是。

后续新增页面时，先用一个 H1 定调，再放任务本身。不要为了让版面显得“完整”自动补 eyebrow 和
副标题，也不要让通用组件强制每个空状态写一段说明。
