# Mufy 角色迁移为什么必须“原样搬运 + 显式缺口”

> 当前实验结果与后续简要迭代统一见[迁移实验主报告](../research/mufy-migration-experiment-report.md)，详细案例放在其附录。

> 技术使用手册见 [Mufy 角色卡批量迁移流水线](../handover/mufy-card-migration-pipeline.md)。

## 过去为什么反复出问题

之前的迁移工作不是没有数据，而是数据被几套一次性脚本分别处理：一套拆 Prompt，一套补图片，一套恢复美化，一套修侧边栏，且多数写死角色名和数据库 ID。只要换一张卡，就容易发生三类问题：

1. 把开场白误当成小剧场，造成演绎室内容错误；
2. 看见原始代码在寄情上暂时不工作，就直接重构成“AI 风格”的新页面，视觉不再是 Mufy 原卡；
3. Prompt、线上详情和数据库各用一部分，没有统一的来源校验，最后无法证明哪一段来自哪里。

因此新方案不是继续增加“更聪明的生成”，而是先建立可核对、可重放、可持续升级的迁移链路。

## 为什么需要三个输入源

完整 Prompt JSON、Mufy 线上详情和登录页面运行态快照承担不同职责，不能互相替代：

- Prompt JSON 负责模型行为：人物、关系、逆境、默认认知、剧情推进、输出协议和文风；
- 线上详情负责用户实际看到的版本：开场白、头像、背景、作者说明，以及 `optimizationCode` / `codeRenderContent` 视觉载荷。
- 运行态快照负责详情接口没有表达的事实：动态注入后的侧栏/手机/播放器 DOM、真实资源请求、组件位置，以及需要本地化的图片和音频。

只有 Prompt，没有小剧场明文时，脚本不能凭开场白“猜”一个演绎室；只有详情，没有完整 Prompt 时，角色可能外观正确但说话完全不对味；只有详情而没有运行态，代码看似齐全，仍可能出现 CDN 403、侧栏未注入和宿主布局错位。三份输入合并并通过视觉验收后，才是一张完整可聊的角色卡。

## 为什么不重新设计原卡美化

迁移的目标是复现来源卡，而不是展示 AI 的视觉创意。作者的 CSS、HTML、脚本和交互结构本身就是设计结果；真正需要改变的只是寄情与 Mufy 宿主页面之间的接口差异。

因此迁移脚本只做四类确定性适配：

- `optimizationCode` 中的 `mufy_` 宿主 selector 转换为寄情的 `nj_`；
- `codeRenderContent` 始终留在组件沙箱，绝不把组件内部 CSS 扩散到宿主页面；
- 把运行态可读取的媒体复制到寄情存储并替换 URL；
- 交给寄情已有的 iframe、悬浮层、parent shim 和安全作用域处理运行环境差异。

如果某张卡仍显示异常，应该扩展通用兼容层并加回归测试，而不是把原始美化删掉重做。这样修一次，同结构的后续卡都会受益。

## 为什么缺失数据必须留空并报告

“看起来完整”不等于“迁移完整”。当 Mufy 接口没有给出某个字段时，自行补内容会混淆来源，之后既无法对比，也无法复原。特别是：

- 开场白不能代替小剧场；
- Prompt 中的 HTML 示例不能自动认定为全局美化；
- 道具不能随意塞进人物设定；
- 没拿到的正则规则不能靠猜测重建。

迁移报告把缺口变成结构化 issue。拿到新导出后，使用同一角色 ID 重放即可；这比先造一个近似版本、再人工追查错误可靠得多。

## 为什么默认 dry-run、私有和 TEST-only

角色 Prompt 是高价值资产，视觉代码还可能包含大段脚本。直接写库的风险不仅是“写错一行”，还包括覆盖人工调整、误写正式库和把半成品公开。

所以流水线把审核分成两步：先解析并出报告，再显式提交。提交还要同时通过 scope、数据库 hostname、owner 和角色名检查；新卡默认私有。这些限制不会增加日常迁移的核心工作量，却能把最昂贵的误操作挡在事务之前。

## 这套方案如何随卡片数量增长

后续每遇到一种新结构，就把它变成“通用适配器 + fixture + 回归测试”。迁移能力会逐步覆盖更多卡型：新的侧栏、新的灵动岛、新的状态栏模板、新的资源结构。原始输入和 SHA-256 清单始终保留，因此解析器升级后可以批量重放，而不需要再次向别人索要全部材料。

最终形成的不是“一键抄某一张卡”的脚本，而是一个来源清晰、差异可见、迁移可回放的 Mufy 兼容层。

## 为什么“写库成功”不能再叫完成

2026-10-15 五卡人工复核再次证明：文字完整、无溢出、按钮能开，不代表美化和行为保真。当前新增“原站实际开场渲染合同”，补齐接口未携带的渲染结果，并把多视口、多页面、折叠往返和真实输入值纳入完成门禁。仍须区分确定性程序检查与 Agent 视觉判断；门禁读到16个通过标记不等于程序自己具备识别所有视觉错误的能力。精确开场合同也不能替代未来任意模型回复的渲染协议。相关实现及边界见 [技术交接](../handover/mufy-card-migration-pipeline.md)。

余斯是和宋聆语暴露的最后一个盲点是：结构与资源都正确，并不等于用户看到的页面正确。悬浮猫咪可能被放进正文流，弹层可能被父容器裁掉，输入框伪元素文案可能丢失，思考按钮也可能保留外观却默认展开。它们不会让数据库报错，也不一定触发 CSS 安全警告。

因此完成定义从“两阶段”升级为“三阶段”：

1. 来源完整：Prompt、详情、Mufy 运行态齐全；
2. 确定性迁移：解析、资源本地化、宿主适配并写入测试服；
3. 结果验收：重新抓寄情运行态，与来源视觉合同比较。

第三阶段检查的是可观察结果，而不是要求两边 CSS 文本一致。两个平台 DOM 不同，但气泡是否存在、悬浮件是否固定并完整可见、输入框文案是否一致、思考是否默认收起、资源是否加载成功，都是可以机械判定的事实。只有这一层通过，Agent 才能把状态从“已导入”改成“已搬完”。

推荐的人机边界是“人只处理身份挑战，Agent 处理迁移”。用户第一次在内置浏览器登录，后续来源详情直接包含在无 token 的运行态快照中；Agent 不需要保存密码。验证码、登录过期和站点风控属于必须交还给用户的身份边界，其余预检、测试服写入、手机/桌面验收和原位重试都由稳定任务状态串联。这样新聊天恢复的是迁移阶段，而不是重新猜测上一轮做到哪里。

角色名只是发现线索，不是身份。编排优先使用 `roleId`；缺少时才在登录态搜索，并用 Prompt 开场、头像和作者缩小候选。只有唯一候选才能进入迁移，避免“自动化”变成自动搬错同名卡。

## 开场正确仍不代表后续回复正确

原站把角色详情和渲染规则分开加载。只还原开场外观会遗漏后续生成内容的转换链；继续逐卡猜模板，容易把固定示例当作通用能力。本轮改为采集真实独立规则，保留顺序和字段，并用不同于开场的新值验证。

规则完整也不等于排版完整：状态栏两列和滚动区还依赖原站整体皮肤，以及多段组件之间共享的页面上下文。迁移应把规则输出与整体皮肤放入同一个隔离画布，不按HTML围栏拆成互相隔离的文档。组件级观测只能证明该组件的修复；五卡跨页面、跨视口及折叠往返仍须单独验收。

自动检查应区分来源完整、协议转换、网页交互和五卡成品验收。规则全部触发只证明转换覆盖；当前用户名、按钮实际填写、动态组件、折叠后高度和资源加载仍须观察真实结果。失败应进入可复用兼容配方及回归样本，不由用户反复人工发现同一个问题。

## 为什么批量迁移仍然要求 roleId 映射

2026-10-15将检查计划补成可执行的通用浏览器检查器。实际运行暴露出三个检查器自身的问题：图片尚未加载就被判坏图、整批检查超时导致内存证据丢失、多条消息复用同规则名导致定位歧义。分别补入有界加载等待、逐状态断点保存、按实际组件实例定位。检查器也需要用真实页面回归，不能只验证它会输出“通过”。

本轮保存五卡80个内嵌结构与原生折叠状态，396次点击；五卡结构检查通过，媒体等待逐项留账。检查结果已接回迁移状态及修复队列，既有兼容配方可显式自动启用。结构通过只证明这一层，完整视觉、源组件含义和定制交互仍由执行Agent比对。普通问题由Agent处理，不能把尚未自动完成的环节写成用户必须复核。

本轮自动化修复的验收教训：不能用按钮出现、显示“已填入”、外层不溢出来判成功。真实输入框值、内嵌组件自身溢出、展开/收起高度、关闭按钮可点击和音频实际readyState都要验。移植兼容配方、历史状态、批量原位更新和浏览器检查计划均应复用；未知结构不应凭假通过进入完成状态。用户明确授权的媒体缺项可以后补，不是拿来掩盖能修却没有修的交互错误。

2026-10-14 用户明确将媒体与轻量装饰缺项定义为后补项。因此“身份/正文合格”“已写测试服”“完整交互合格”应分开记录，不能继续用音频缺项否定已确认角色，也不能因为写库成功就声称成品完成。首批五张已写入；资源与装饰差异保留可追溯清单，继续修通用适配。年龄取已授权底稿而非不一致的基础元数据，原文不改。执行计时只汇总已记录阶段，分析开发墙钟单列；源/目标映射核对防止断线后重复创建。

平台搜索只能帮助发现候选，不能证明候选就是提取 Prompt 对应的原卡。同名角色、标题追加版本说明、作者改名、私有卡和下架卡都会造成误匹配。批量 Agent 因此采用“两把锁”：先要求显式 `roleId/source_url`，再比较线上开场白与本地 Prompt 开场白的可见正文指纹。名字相同但正文差异过大的卡照样拒绝迁移。

这项限制看似增加了一列数据，实际避免了最难排查的失败：页面、美化都正常，但人物内容来自另一张同名卡。对无法从搜索确认的角色，正确做法是让原始万人数据保留来源 ID，而不是让 Agent 自行猜测。

2026-10-19：固定开场恢复与后续规则渲染是两条独立路径。“开场正常”不能外推“连续聊天正常”。后续回归需同时检查外层透明、内部卡片保色、系统可见框及动态状态栏，不能只数规则命中和横向溢出。页面皮肤进入消息iframe时必须重新处理背景的作用域，不清空所有元素背景。技术细节见[迁移交接](../handover/mufy-card-migration-pipeline.md)。

2026-10-19 完成门槛补强：Agent 不再允许开场通过就标记整卡完成。至少两条不同后续消息、手机/桌面、展开/收起/重开全部留证；旧状态要重新核对当前版本。普通缺陷进入Agent修复队列，而不是转交用户找问题。离线合成样例用于提前暴露协议回归，真实已有聊天用于验收，二者明确区分，不用“测试很多”掩盖缺少成品证据。此次改的是本地Agent验收流程，未修改线上聊天行为或数据库；首批五卡还不能宣布全部成品合格。合同与剩余边界见[技术交接](../handover/mufy-card-migration-pipeline.md)。

同日实际执行80个结构状态的进一步教训：检查工具也会制造假问题或假证据——请求手机宽度不代表实际变小，宿主缩略图不代表手机截图，点击返回不代表toggle事件已稳定。现在把实际视口、PNG像素几何、控件稳定状态分别核验，并逐步落盘。已完成结构检查不替代来源视觉判断，也不擅自消耗银币补造聊天记录。下一批继续五张，先完成本批收口，不以扩大量掩盖质量缺口。

续跑进一步证实：尺寸正确的PNG也可能是隐藏浏览器未重绘的旧画面，必须检查截图是否真有当前回复。实际显示后发现原站平台提供的表格交替底色也是迁移依赖；漏掉这层，开场可正常而后续黑字难读。修复应由源站公开样式事实驱动、限定迁移组件，不用全站强制改色遮盖问题。用户已授权正常银币测试，8条真实回复现已补齐；仍不能把“回复生成成功”写成“成品验收完成”。下一批按5张固定流程执行，并从真正开始时记录各阶段实测耗时，等待和并发不得美化成净工时。[技术交接](../handover/mufy-card-migration-pipeline.md)

## 2026-10-21：把卡点收敛到具体证据，而不是持续重跑

五张后续回复报告已通过，但开场、媒体和辅助交互不能由此自动批准。本轮新增开场独立范围、实际布局稳定采样、稳定后精确聚焦，以及显式补图引用：Tab 会把焦点移往固定辅助入口，单纯“获得焦点”不代表当前回复可见；需要用不改变控件状态的修饰键定位并看实际图。隐藏火焰辅助入口也不能被算作正文折叠栏，更不能从统计中悄悄消失，必须原始留存、单独声明未验。

80个新开场状态已实测和逐图复核，真正剩余问题包括浅字白底评论、空音源却变成暂停的播放器，以及未有完整可见证据的宠物气泡。将这些写成具体差异与下一步，不再用“只剩收尾”掩盖。浏览器观测的13.03分钟只是已记录步骤之和，既不是墙钟耗时，也不是整个 Agent 净工时。详见[技术交接](../handover/mufy-card-migration-pipeline.md)。

## 2026-10-21 本版验收收口

本版五张当前迁移格式的开场与两条独立回复已完成160个状态的实际复核和严格报告校验。评论浅字、空播放器假暂停与后续终端缺共享组件样式已分别处理，不再把“编译成功”写成浏览器完成，也不再无限重跑同一版本的成功页面。

源组件样式不能只看首屏：创作者可把终端CSS放在开场、正文放在后续。修复应把独立来源组件皮肤限定传给对应沙箱，既保留作者样式，也不向宿主导入整页主题。精确定位还纠正了早先误把终端当占位的判断。与此同时必须公开范围：风满楼最早旧原生回复未回写，缺失外部媒体仍延期；不能拿新版两个样本通过去宣称所有历史和媒体完美恢复。

下一批仍五张，由Agent承担来源预检、重复检查、迁移与开场/后续回复双端验收；不把生成文件或完成计数当成可交付卡。时间分步骤实测，排除用户停留和调度间隔。最新事实以 `release-closeout.json` 为准，见[技术交接](../handover/mufy-card-migration-pipeline.md)。

## 2026-10-28：开场像，不等于后续真的能用

本次30张暴露出采集契约缺口：公开开场可以已经是渲染结果，未来回复却仍需要原站的完整有序转换链。“设置没有可见规则”也不等于没有渲染规则；傅司晏实际加载3条。获得明确授权后才读取正常页面规则响应，未扩展到凭据或私有人设。

因此把“真实响应已采集”“规则已补入并重载确认”“已有回复组件能显示”“颜色和交互通过”“整卡验收”拆开记录。16条非空链已补齐，不自动给28张签通过；白底邮件文字被全局白字覆盖就是结构成功、视觉失败的例子。真实修复应保留组件自己的画布边界，而不是统一改成平台配色。

还要把编辑后回归纳入Agent：原生表单将LF变CRLF，本不应让整条链失效；加入兼容回归能避免“刚修好，编辑一次又坏”。同理，恢复时间栏后要检查台词头像，而不是单点通过就交给用户返修。技术和当前发布状态见[技术交接](../handover/mufy-card-migration-pipeline.md)。

## 2026-10-31：默认值也属于迁移，不属于平台接管

作者没写 font-family，不代表迁移平台可以任意改成自己的字体。两张实际卡的独立文档默认值都被平台 reset 替换；恢复应限定在来源独立文档，并让作者声明覆盖默认值，不把所有卡硬套同一字体，也不声称字体名称一致就证明远端字体文件已成功加载。

验收同样不能只看表面信号：64px 过期提示图也是“加载成功”，PLAYING 文字可以对应零进度，切换时旧面板文字可以暂时还在。Agent 要保存真实资源资格和稳定交互状态，把来源失效、待发布修复、当前 TEST 对应及整卡验收分开。当前批次依然没有整卡签收，也没有为了补通过数提前构建。实现范围与证据见[技术交接](../handover/mufy-card-migration-pipeline.md)。
