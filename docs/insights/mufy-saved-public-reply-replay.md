# 不把局部回放当成整卡验收

技术操作见 [交接文档](../handover/mufy-saved-public-reply-replay.md)。

开场组件检查不足以说明后续回复正常；已保存公开回复可以在不新增模型请求的情况下，经真实渲染器复验折叠和协议处理。

但回放的规则必须完整。只加载来源规则链、漏掉已经核实的兼容规则，会把测试装置缺陷误判成产品回退。原文与完整规则分别绑定指纹，能避免错用旧结果。

验收结果需要拆开：结构控件、指针交互、手机布局、来源视觉、外部媒体、真实生成及测试服集成。键盘兜底、分步成功、原站资源失效都应写明条件；不能为了凑通过数抹掉失败。

自查自修的目标是减少人工返修，而不是用更多自动检查数字代替真实用户体验。当前快速连续点击异常依然是异常；初始布局无溢出也不代表所有弹层、展开态与触屏都已通过。

单个组件验证之后，还要验证最终候选的组合挂载。反过来，组合装置不能复制所有真实 ChatRoom 行为后就冒称端到端：它禁用了模型、账户及外部网络，只能证明其明确检查的节点与交互。

重绘测试尤其要控制焦点。前缀面板本来就应在焦点离开时关闭；聚焦外部“模拟重绘”按钮会引入额外变量。通过页面上的定时重绘按钮先排程、再正常打开面板、等待明确的重绘计数变化，才能观察不移焦点的真实状态保留。此轮三个前缀面板都能保留，不需要为测试装置的误报改掉产品关闭语义。

收尾还要防止“记录回退”：本批汇总器不应重算旧批次结论，也不能用“已导入”覆盖一个后来确认的范围暂缓。每批写入边界应明确，旧行在写前核对完全不变，暂缓与导入分别计数。

完整验收、发布前检查与更新后的集成验收是三个不同关卡。先全部验好再构建的约束，不能靠把本地夹具叫作线上验收来绕过；如果剩余验收必须依赖测试服更新，应明确请求受控阶段调整，保留媒体与截断等真实未通过项，而非无限重复已通过的局部测试或擅自改成通过。
