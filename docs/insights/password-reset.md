# 忘记密码 / 重设密码（产品思考）

> 配套技术交接：[../handover/password-reset.md](../handover/password-reset.md)

## 起因不是「补功能」，是「救迁移」

这个入口不是排期里的正常需求，是上云迁移逼出来的。老用户从自托管 Supabase 迁到云端，
密码哈希能否原样带过去是**不确定**的（GoTrue 没有官方「导入任意 bcrypt 即可无感登录」的路径）。
一旦有人迁完登不进，而 app 又没有任何找回入口，那就是**把老用户锁在门外**。所以这条链路
先于「优雅」存在 —— 它是迁移的安全网，也顺带成了日常找回密码的常规出口。

## 三个取舍

**1. 防枚举优先于「友好报错」。**
填了没注册的邮箱，我们不告诉用户「查无此邮箱」，而是统一回「如果这个邮箱已注册，信已发出」。
这牺牲了一点即时反馈，换来不泄露「谁注册过」。对一个零内容审核、用户对隐私敏感的平台，
这个方向是对的 —— 注册关系本身就是隐私。

**2. 复用而非新建认证机制。**
重置链路整个搭在既有的 `/auth/callback` + PKCE 之上，和注册确认信同一套。没有引入新的
token 体系、没有自建一次性链接表。少一套代码就少一处能出错、能被绕过的地方。

**3. 改密后强制重登。**
本可以让恢复会话直接变成正常登录、省一步。但重设密码是敏感操作，用户的心理预期就是
「改完要重新登一次」，而且强制重登能验证新密码真的记住了。多一步点击，换确定性和心理一致。

## 留给未来

- **限流**：目前发信频率靠 Supabase / Resend 侧兜底。若被刷，考虑在 `/api/auth/forgot-password`
  加 IP / 邮箱维度的节流。
- **迁移密码的最终策略**：见 [../handover/supabase-cloud-migration.md §2.2] 的三选一（无感 / 全员重置 /
  首登拦截）。本功能让「全员重置」这条路可行且不难受 —— 哪怕无感登录没做成，用户也能自救。
- **i18n**：英文文案已铺（en.ts），v1 中文优先，上线先跑中文。
