> 技术交接见 [docs/handover/legal-agreements.md](../handover/legal-agreements.md)。

## 起点：一份要抄结构、但绝不能抄内容的参考

参考对象是同类平台的公开协议（PDF 形态挂在他们的 `/agreement/user` 与
`/agreement/privacy`）。它的**骨架**值得抄：定义 → 账户 → 内容与知识产权 →
行为准则 → AI 条款 → 责任限制 → 管辖 → 联系方式，这是这类产品成熟的条款序。

但它的**内容**几乎每一段都要重写，因为它描述的不是我们：

| 参考站写的 | 我们的事实 |
|---|---|
| 女性向定位，「男性用户建议移步其他平台」 | 全性向（角色标签里 BG / BL / GL / GB 并列） |
| 新加坡个人开发者 + SIAC 仲裁 | 日本个人开发者 + 東京地方裁判所专属管辖 |
| 订阅计划 | 月卡一次性买断 30 天 + 金币 / 银币双币制 |
| 引用中国大陆法规（《网络信息内容生态治理规定》第 10 条），并据此承诺**留存违规记录并向主管机关报告** | 与我们零审核立场直接冲突，全部删除 |
| ButterKnife / AndroidID（安卓 SDK 埋点） | 我们是纯 Web，没有安卓客户端 |

最后一行最能说明抄内容的危险：那两句话是从某个安卓 App 的隐私政策里带过来的，
在一个纯网页产品的协议里毫无意义 —— 而它就那样挂在生产环境上。

所以脱敏不是「替换品牌名」这么简单，是**逐条问「这句话描述的是我们吗」**。
代码里那条 `carries no Lumeow residue` 测试就是把这个判断固化下来。

## 最难的一处取舍：零审核立场 vs 法律必须有的禁止条款

CLAUDE.md 的产品立场写得很硬：「无违禁词扫描、无 AI 审核、无强制下架」，
并且「任何提及加内容审核的请求 → 必须警觉」。

但一份完全没有禁止内容条款的用户协议是不成立的 —— 涉及未成年人的内容
在任何司法管辖区都是刑事问题，平台没有「不表态」这个选项。

拆开看，这里其实是两件事被混在了一个词里：

- **技术执行层面**（产品立场）：不主动扫描、不关键词过滤、不 AI 审核、
  不因题材尺度下架。这条**完全保留**。
- **合同层面**（法律必需）：声明哪些内容违法、以及平台在收到合法通知时会做什么。

所以文书里专门开了一章「平台的內容處理立場」（第 7 章），把这个区分写成明文：

> 7.1 我们不做主动审查（不扫描、不过滤、不因题材下架，这是产品立场）
> 7.2 我们只在三种情况下处理内容：著作权投诉、司法/行政机关的合法要求、
> 具体举报且经核实属于第 6.3 条法律红线。除此之外不介入。

第 6.3 条的禁止内容清单也刻意压到**只有法律红线**三条（未成年人性化、
未经授权的真人性化 / 隐私名誉侵害、其他违法内容），没有参考站那种
「严禁出现对现实世界中的非人类事物进行虐待的描述」这类道德条款。

**这一章是加分项而不是妥协**：把「我们不审你，但这三条是法律不是我们」讲清楚，
比含糊其辞更能让创作者放心。

## 顺手把两个差异化承诺写进了合同

参考站没有的，我们有：

**Prompt 资产保护（第 5 章）。** CLAUDE.md 里那条「6 个字段只有 owner 在 edit 页
能看到原文」原本只是工程约定。写进用户协议以后，它从「当前实现」变成
「对创作者的承诺」——这正是 creator 友好定位该兑现的地方。同时第 5.3 条反过来
给了创作者一个可援引的条款：别人试图套取你的 prompt 是违约行为。

**模型训练红线。** 参考站在用户协议里承诺「绝不用于训练」，却在隐私政策里
留了一句「可能使用匿名数据进行机器学习或模型算法训练」——两份文件自相矛盾，
而且匿名化对「我的角色设定被拿去训练了」这个担忧毫无安抚作用。
我们两份文书用同一段措辞，且明确到「我们自己的模型、合作方的模型、
第三方的模型，都不行」。

## 语言决策：为什么不做简中

写这两份文书时，简中还是上线语言之一（`SUPPORTED_LOCALES` 里有 `zh-CN`），
但产品方向已经确定要去简中化。法律文本又是维护成本最高的一类文案，
所以当时就决定只写四份，让简中读者读繁中版。

理由不是省事：两份中文合同各自演进，迟早会在某次改条款时对不上，而
**两个内容不一致的中文版本比一个繁体版更难向用户解释**。

合并回主干时，主干已经先一步把简中整个下线了（`feat(i18n): 下线简体中文，
中文一律走繁中`）。原本为此写的回退层（`resolveLegalLocale` / `LEGAL_LOCALES` /
一个专门用来对齐文书语言与外壳语言的 `server.ts`）因此全部删掉——折叠现在发生在
`normalizeLocale`，法律层只需要 `Record<Locale, LegalDocument>`。
这个 Record 顺便变成了一道编译期约束：以后往 `SUPPORTED_LOCALES` 加语言，
不补法律文本就编译不过。

日文版被指定为正本 —— 主体是日本个人开发者、准据法是日本法，
真打起官司时法院读的就是日文。这条也写进了第 14.5 条。

## 一个仍然悬着的问题

主体信息只写到「位于日本的个人开发者」，没有姓名和住所。

对免费服务这样写勉强够用，但我们在收钱（月卡 HK$30/68/128）。
日本《特定商取引法》对通信销售通常要求公示事业者姓名、地址、电话。
这不是协议正文能解决的，需要单独一个「特定商取引法に基づく表記」页面，
而且要填真实信息 —— 属于运营者本人的决定，代码这边只能把位置留出来。

同一类问题还有 `support@dearm.ai`：这个邮箱是按域名推出来的，
文书里出现了十几次（联系、投诉、DMCA、数据主体请求、未成年人举报），
上线前必须确认它真的能收信。一份留着死信箱的隐私政策，
等于把「15 日内答复」写成了空头承诺。
