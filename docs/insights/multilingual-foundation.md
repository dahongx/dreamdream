# 多语言第一阶段：产品思考

**技术交接：** [multilingual-foundation.md](../handover/multilingual-foundation.md)

## 为什么是繁中、日语、泰语

这三个市场的共同点不是“都在亚洲”，而是角色扮演、女性向叙事、二创文化和长文本付费意愿之间有明显交集。繁中还能以较低内容迁移成本验证跨地区运营；日语对角色语气和人设一致性要求高，能倒逼产品质量；泰语市场更适合验证 Dearm 能否真正走出汉字文化圈。

因此第一阶段的成功标准不只是“按钮能切语言”，而是四件事同时成立：界面完整、输入法友好、字体正确、模型真的用目标语言稳定续写。

## 关键取舍

### 1. 目标市场优先，不删除旧语言

把繁中、日语、泰语放在选择器前面并以繁中作为未知环境默认值，体现产品方向；保留简中和英文，则避免现有用户突然失去熟悉界面。旧 `zh` Cookie 继续代表简中，是一次有意的兼容决策。

### 2. 先完成产品内语言，再动 URL

现在把 90 多个路由迁入 `[locale]` 会同时触碰 Auth、Stripe、分享链接、Server Actions 和大量硬编码跳转。第一阶段先用 Cookie 验证真实使用率和留存，等市场信号成立后再做 SEO 路由，风险和返工都更可控。

### 3. 不把 UI 翻译等同于角色内容翻译

角色名、简介、作者的话和 prompt 原料属于 creator 内容。自动把它们随界面语言翻译，会损伤人物语气，也可能暴露受保护 prompt。第一阶段只翻平台文案并控制模型输出语言；creator 内容多语言应当是独立的数据模型与授权工作流。

### 4. 主模板翻译必须有证据门槛

上游数据中的日语/泰语角色卡样本只足以支持回归评测，覆盖率远不足以构成新的主模板。当前选择经过校验的英文 instruction units，再额外要求模型用繁中/日语/泰语输出。它不如原生模板理想，但比未经验证的机器直翻更可控，也保留后续 A/B 的清晰基线。

### 5. 创作工具也必须说同一种语言

如果界面已经切成日语或泰语，但 AI 美化助手仍输出简中组件名、提示词和占位文案，creator 会把它理解成“翻译皮肤”，而不是完整产品。因此聊天和创作工具必须共享同一个 locale 决策；同时只翻译人会读到的内容，XML、selector、变量与 proposal 协议保持全球一致，才能兼顾体验和资产可移植性。

### 6. 稳定数据与本地化展示必须分层

角色标签、官方包、官方规则和钱包流水都已经存在存量数据。如果为了翻译直接改数据库值，会让筛选 URL、订阅关系、规则 ID 和审计记录随语言抖动。第一阶段采用 locale-neutral canonical 数据，在请求或展示边界投影文案；这套模式也应成为以后所有内置资产的默认做法。

### 7. 付费与分享不是外围页面

用户会在 Stripe 托管页、支付回跳、社交分享卡和 PWA 安装面判断产品是否真的属于自己的语言。它们虽然不在主聊天画面里，却直接影响信任与转化。因此“多语言完成”的验收必须包含外部托管支付、异步履约文案、OG metadata 与 manifest，而不能只数 React 页面上的翻译 key。

## 接下来应看什么

- 各 locale 的注册转化、首聊成功率、第二日回访和付费转化。
- 首次回复是否混入简中/英文，以及标签、HTML、变量被翻译破坏的比例。
- 创作者 AI 的说明、组件可见文案与槽位名是否混入简中，以及生成 proposal 的应用成功率。
- 同一角色在三种语言下的人设一致性、语气自然度和格式通过率。
- 用户是否频繁在 UI 语言与聊天语言之间来回切换；若明显存在，应尽快拆出 session 级聊天语言选择。
- 各 locale 从分享卡点击到注册、从 Checkout 打开到 webhook 成功履约的漏斗差异。

这些数据足够后，再决定优先做 URL 国际化、creator 内容翻译，还是原生主模板本地化。
