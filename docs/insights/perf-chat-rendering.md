# 聊天页性能优化（产品思考）

> 技术交接见 [docs/handover/perf-chat-rendering.md](../handover/perf-chat-rendering.md)。

## 为什么这批优化值得优先做

用户反馈的三个症状（打开卡 / 输入卡 / 越聊越卡）在长对话产品里是致命的：
我们的核心用户画像恰恰是「跟一张卡聊几百轮」的深度玩家 —— 产品体验最差的
时刻正好落在最忠诚的用户身上，且随使用深度恶化。这跟一般 SaaS「重度用户
容忍度高」的规律相反，必须当 P0 修。

## 取舍记录

**上下文滑窗 60 条**：这是产品决策不只是技术决策。角色扮演的沉浸感主要靠
（a）system prompt 里的人设/世界观（每轮全量重建，不受窗口影响）和（b）
最近 30 轮左右的剧情短程记忆。60 条以外的细节对生成质量的边际贡献，撑不起
它带来的 first-token 延迟和 token 成本 —— 后者随会话长度线性烧钱，直接吃
毛利。钉住开场白是刻意的：它是角色的「定场戏」，丢了模型容易人设漂移。
将来若做「长程记忆」（摘要 / 检索），入口就在 `truncateHistory`
（lib/ai/history-truncate.ts，合并时采用了 main 侧因内存事故并行落地的
字符预算版实现）。

**没做虚拟化**：收益真实但改动大（贴底滚动、ResizeObserver、creator CSS
对 DOM 结构的依赖都要重新验证）。这批 memo 化之后，长会话的增量成本从
「每次交互全列表重算」降到「只有 DOM 体量」，预计能撑到几百条消息；虚拟化
留给数据说话 —— 如果用户真的普遍聊到 500+ 条再立项。

**债务变资产**：iframe Host API 的 bridge 断裂 bug（第二轮对话起
getHistory/sendMessage 失联）是顺着性能问题挖出来的 —— 创作者做的交互小
剧场此前实际上只在首轮可用，没人报 bug 大概率因为小剧场创作者少。修好它
是给「creator 友好」这个差异化定位补地基。
