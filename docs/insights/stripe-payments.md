# 产品思考 — Stripe 真实支付

> 技术交接见 [handover/stripe-payments.md](../handover/stripe-payments.md)。

## 为什么现在做

付费的「账」侧（双币、月卡、签到、账本、成本结算、admin 充值）早已齐备，缺的只是
真实收款。同时旧的 `subscribeToTier` 对任何登录用户开放、点一下免费发卡 —— 既是上线
硬卡点也是收入漏洞。这次把「钱」接上，并堵掉漏洞。

## 关键产品约束塑造了技术选型

**「主要面向大陆，必须支持支付宝 + 微信」这一条几乎决定了整个架构：**

- 支付宝/微信在 Stripe 下**只支持一次性付款**，不支持订阅/自动续费。
  → 月卡只能是「买断 30 天」，真订阅这条路被支付方式直接否决，不是我们选的。
- 它们是异步重定向型支付 → 履约必须以 webhook 为唯一可信信号，前端跳回只是反馈。
- 收银台用 Stripe Checkout 托管页：一行配置就能动态展示卡/支付宝/微信，还自动处理
  3DS、移动端、二维码 —— 自建 Payment Element 要管的状态多得多，跑通阶段不划算。

## 取舍

- **HKD 计价**：原计划 USD，但实测账号是香港主体、微信只收 hkd/cny，USD 直接让微信不可用。
  改成 HK$30/68/128（整数运营价）。代价是大陆用户看到的是 HK$ 而非 ¥，可接受；若要 ¥ 标价
  改 `CURRENCY='cny'` 即可（也支持支付宝/微信）。
- **Adaptive Pricing**：账号默认开了自适应定价，会按访客地理位置覆盖币种 —— US 访客被切到 USD
  后微信消失。这是「能不能服务大陆用户」的隐形开关，上线前要么关掉它、要么确认 CN 访客拿 CNY。
- **托管页 vs 内嵌**：托管页牺牲了一点暗紫黑设计一致性（跳到 Stripe 域名），换来最快、
  最稳、最广的支付方式覆盖。对「先跑通生产支付」这是对的。内嵌可作后续视觉打磨。
- **订单表独立于流水**：`payment_orders` 记支付生命周期 + 幂等，`currency_transactions`
  继续记余额变动。分开后现有账本/审计 UI 零改动，支付侧也有干净的对账面。

## 留给运营/后续的事

- Dashboard 启用支付宝/微信 + 确认账号注册主体满足资格（大陆主体通常不行）。
- 退款、发票、到期提醒、自动续费（若未来上银行卡专属续费档）。
- 「直购」（按需买银两）仍占位 —— 可作为下一个收入点。

## 风险

- Stripe 在大陆的可用性取决于商户主体注册地，这是产品能否真正服务目标用户的前提，
  需在上线前用真实账号确认，而非代码问题。
