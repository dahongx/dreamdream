# 整站界面升级：产品思考

> 技术交接见 [docs/handover/ui-replacement.md](../handover/ui-replacement.md)。

---

## 为什么这次换皮要整站替换，而不是换肤

产品已经进入有真实付费用户的阶段。当前的「暗紫黑 + 月光金 + 玻璃卡」是 v1 从零搭起来时的视觉，当时的首要问题是「能不能跑通」；现在的问题变成了「第一眼能不能让人相信这是个值得投入情绪的地方」。

换肤（只改颜色和圆角）解决不了这件事。当前界面的信息结构本身带有早期痕迹：探索页把角色当成卡片格子、详情页把设定当成资料页、聊天页把控件堆在正文周围。这些结构决定了「这是工具」而不是「这是入口」。

所以定的是整站替换，且要求**看不出是同一套**。这是有意把标准定得比"好看一点"高。

---

## 三条候选背后是三种不同的产品判断

不是三种配色，是三种关于「用户为什么会留下来」的假设。

### A 午夜影院 —— 假设是「被故事击中」

大幅人物、剧情海报、场景式聊天。首屏只讲一件事：今晚走进谁的故事。

这最贴产品定位（"暗夜读小说"）。代价是**首屏只装得下一个人**，老用户回来找上次聊的角色要滑。对新客吸引力最强，对留存最弱。

### B 心动频道 —— 假设是「找得到人」

双列卡片、搜索置顶、最近对话并列。像日常打开的陪伴应用。

这个假设最符合实际使用：角色扮演平台的钱在复访，不在首访。但它有**品类通用性风险**——做得好会像所有同类产品，做得保守会像后台。

### C 私语档案 —— 假设是「读得下去」

横向角色条目、稳定阅读底色、连续小说排版。

这解决了当前最真实的一个问题：**中文长段落在这个产品里是主体内容，但界面一直按短消息设计**。缺点是第一眼冲击力最弱。

### 为什么推荐 B 而非 A

B 在"发现效率"和"日常可用"上最优，是三者里唯一能同时服务新客和复访的。但推荐里吸收了 C 的阅读排版——因为 A 和 B 都解决不了长文阅读，而那是产品的核心消耗场景。

**这个推荐尚未被用户采纳。** 用户明确说过原概念图的区分度比后续原型好，方向仍在讨论。

## 这件事上我犯过的错误，值得记下来

### 错误一：把"手机优先"做成了"只做手机"

用户给的是桌面网页 + 手机聊天的完整构图。我在做可点击原型时，全部收成了 390px 窄屏。

理由当时听起来正当——手机是主要场景。但**手机优先是适配顺序，不是砍掉桌面**。原型只有窄屏，评审对象就看不到侧栏、最近对话区、角色展示这些真正决定气质的部分。结果三套看起来只是换了颜色，用户当场指出来"看不出区别"。

这是执行偏离，不是需求变更。记录下来是因为它容易再犯：一旦拿到"移动优先"这类要求，就要警惕用它当借口缩减交付范围。

### 错误二：把生成图当成了设计源头

生成的概念图好看，但**它的细节是画出来的，不是排出来的**。有些排版在真实 CSS 里做不出同样的质感，有些字体组合在中文里不成立。

后续可点击原型比概念图"丑"，一部分原因就在这里——但我当时没有讲清楚，导致用户以为是我做退步了。

正确做法：概念图只用来定方向（配色、气质、信息优先级），落地时明确告知"哪些细节无法 1:1 还原"。

### 错误三：技能讲成了流水线

第一版汇报把四个 skill 写成了一条顺序流水线，读起来像"四个工具自动产出了这套界面"。

事实是：`frontend-design` 只是说明文档（24 KB，无脚本）；`web-design-guidelines` 只出报告不改代码；网页全是手写的。把工具的作用说大，短期好看，长期是给自己埋坑——评审对象会以为流程可以复现，或者以为换个工具就能出同样结果。

准确说法见技术交接的第八节。

## 一条产品约束，不是设计偏好

**模型健康状态在没有统计样本时必须显示「待观察」，不能显示「流畅」。**

这条不是视觉问题。同类的模型状态标签之所以能建立信任，是因为它反映真实数据；一旦在无数据时默认乐观，这个标签就退化成了装饰。原型里所有状态统一是「待观察」，也不编造成功率、延迟或在线人数。

真实接入时的判定规则（成功率 < 50% 中断、< 90% 或首字 > 15s 拥堵）已经在 `feat/model-status` 分支实现并上了测试服，有 30 分钟窗口统计和至少 3 次样本门槛。界面换皮时要复用这套数据，不要另造一套。

---

## 最大的未验证风险：创作者美化兼容性

这个产品有一个别家没有的东西：**创作者可以给自己的角色写 CSS / iframe 美化**。这是核心资产，也是界面改版最容易砸掉的东西。

所有聊天页 UI 必须挂 `nj_*` selector，这是已发布契约。换皮如果动了 DOM 结构，创作者写的样式就会全废。

原型刻意没有复用生产组件，所以**它通过不代表接入后也通过**。正式实现前必须先做 selector 兼容性预研——这件事优先级高于视觉还原度。

---

## 不做的事

- 不做 light mode（产品定位是暗夜阅读）
- 不为了"高级感"牺牲中文长段落可读性
- 不在没有数据时制造任何指标
- 不把原型当成可以直接搬进 `src/` 的东西

## 换皮落地后的反思（2026-11-06）

### 一、"独立原型通过" 和 "换上生产能用" 之间隔着一次真实渲染

静态原型里我把三套方向都做出来、截图看着都对。真套到生产代码上，四个问题立刻暴露：

副标题变成一整条色带、桌面 hero 底下空出 500 像素、文案被绝对定位钉在已经不存在的月门图上、手机端那个 ☰ 删不掉。

**前三个是我 CSS 写错，第四个是我搞错了对象。** 共同点是：没有一条能靠读代码发现——原型有自己的 CSS，生产有生产的三层 `@media` 覆盖链（桌面 1080+、平板、手机三档，各写一遍 `height` / `position` / `padding`）。只有真渲染、量 `getBoundingClientRect()`、看截图，才知道规则互相怎么打架。

结论：**换皮的验收单位不是「页面」，是「断点 × 页面」**。1440 通过不代表 390 通过，探索页通过不代表商店页通过。

### 二、删 UI 之前先问它装了什么

用户说"上面那个收纳抽屉不要"。我以为是个装饰按钮，结果它里面是**语言切换 + NSFW 开关**——手机端仅此一处入口。直接删掉，功能就没了，而且不会报错，只会静默消失。

正确的解法不是删，是**把它装的东西摊到台面上**：桌面那组控件本来就在 DOM 里（`hidden md:flex`），手机端允许它显示、把语种名折成图标，两个开关就直出了，☰ 自然失去存在理由。

顺带暴露一个更隐蔽的坑：探索页手机端把标准顶栏 `display:none` 了，改用 hero 里一套绝对定位的浮层顶栏。我按 `#app-topbar` 的 class 改了半天毫无效果——**改的对象根本不在渲染树里**。这类"同一个 UI 有两套 DOM"的旧包袱，在改版时是最耗时的部分。

### 三、把"原版也有"从"我搞坏了"里摘出来

`/creators` 404、`/characters/new` 显示「故人不在此」、个人页中间有个只有图标没有文字的空按钮——这三个看起来都像是换皮事故。

逐一回原版 8091 对照后确认：**全部原版就有**。

这一步不能省。不核对就两个坏结果：一是白花时间修不是自己造成的 bug，二是更糟——把它当"原版行为"记进文档，实际上是自己引入的回归。**唯一可信的判定方式是同一份账号、同一个视口、对原版跑一遍相同操作。**

同理，聊天页背景是棕褐色不是炭黑，也不是皮肤失效——那是角色自带的美化包。**角色的自定义视觉本来就该盖过全站皮肤**，这条边界是对的，不该"修"。

### 四、无头截图卡死 ≠ 产品缺陷

已登录的长列表页在无头 Chromium 里截图会无限超时，一度让我以为页面挂了。根因是 214 张卡各带一层 `backdrop-filter`，无头合成器扛不住；**原版 8091 完全一样**。

绕法是先用一次登录拿 `storageState`，再用全新 context 打开目标页截图。这招值得记下来：**Playwright 里"刚登录完的页面"和"带着登录态新开的页面"渲染路径不同**，前者会持续挂着一些 transition / fetch，后者不会。

### 五、这次换皮为什么能做成"零功能改动"

因为所有视觉覆盖都挂在 `html[data-reskin="siyu"]` 下面，且**只引一个 `<link>`，不改任何组件逻辑**。唯一一处结构改动是给立绘容器包了个 `.nj-card-shot`（手机端要把它从绝对铺满改成相对海报），桌面端行为完全不变。

代价是：这套皮肤的维护性依赖原版 class 名。一旦原版重构 DOM，皮肤会静默失效（不报错，只是回到旧样式）。**这是预览用的临时方案，不是长期架构。** 真上线要的是把这套 token 写进 `globals.css` 本身，而不是叠一层 override。

### 待观察

- 团队看完会给什么反馈：是"方向对、细节糙"，还是"方向本身不对"。前者好办。
- 60 多个角色卡里，有多少带美化包。如果比例高，全站皮肤的实际可见面积会远小于预期。
- 390px 双列在海报比例 3:4.1 下，标题两行截断会不会吃掉太多。现在的取舍是**让名字完整、简介压到一行**。
