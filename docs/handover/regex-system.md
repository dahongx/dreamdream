# Regex System — Handover

> Companion: [insights/regex-system.md](../insights/regex-system.md)

The regex pipeline is the densest creator-facing surface and the
project's #1 differentiator vs competing platforms. Two render paths (sanitize +
iframe) sit on top of one rule schema. This doc describes what's
live; companion handover docs cover the render side
([chat-pipeline.md](./chat-pipeline.md)) and the iframe sandbox
([same](./chat-pipeline.md#regexiframe)).

Surface at a glance:

- Character-scoped `regex_rules` CRUD (`/characters/[id]/regex`)
- Three pure functions in `src/lib/regex/`:
  `applyRegex` (single string out, sanitize-only),
  `applyRegexStreaming` (streaming-safe; trims at last unclosed `<`),
  `applyRegexToSegments` (returns Segment[] for iframe slot carving)
- `buildRegexGuidanceSection()` folds each enabled rule's
  `output_guidance` into the canonical master's `OutputSetting` slot under
  `## Creator-defined output extensions`
- Test panel + template loader inside the editor — bundled with 3
  sanitize-path templates (env panel / dynamic memory / emphasis) and
  1 live iframe-path template (yearn-phone, runs in the sandbox)
- AI authoring helpers wired above each textarea (target-text /
  replacement-html / output-guidance generators — see
  [ai-generators.md](./ai-generators.md))

## Data flow

```
Creator → /characters/[id]/regex/new
  → server action createRegexRuleAction
  → INSERT regex_rules

Chat turn → /api/chat
  → loadRulesAndPrefs(characterId, userId)
  → filterRulesForUser(rules, userPrefs)
  → buildSystemPrompt({ rules })   // Dearm adapter + creator guidance in OutputSetting
  → streamText
  → onFinish: applyRegex(text, activeRules)
  → INSERT messages {
      content,
      renderedHtml,
      debugInfo: { rawOutput, matchedRules, unmatchedRules, systemPrompt },
    }

Chat render (client) → <MessageBubble>
  → expandSpecialTags     (rewrite <message>/<system>/<narration>)
  → applyRegexToSegments  (carve out iframe slots, sanitize html ones)
  → React renders each segment: sanitize → Markdown+rehypeRaw,
                                iframe   → <RegexIframe>
```

## Pattern semantics

`applyRegex()` accepts two pattern forms in `regex_rules.pattern`:

- Bare body — flags default to `gms`. Most common — `<env>(.*?)</env>` etc
- Literal `/body/flags` — creator opts into specific flags. We always force
  `g` so `replace()` does all matches

Replacement is plain `$1 / $2 / $&` semantics (substituted by hand from the
match args, see v1.3). Capture groups generated by the XML-sample auto-derive
line up with `variable_mapping[].index`.

## Visibility + user prefs

Each rule has two booleans:

- `enabled` — owner switch. OFF = rule does nothing for anyone. Precedence
  pinned by test (`regex.test.ts`): enabled=false short-circuits BEFORE
  the userPrefs check, so a stale `user_regex_preferences` row left over
  after a creator toggles enabled off cannot silently re-activate the
  rule.
- `visible` — opt-in for end-user override. When `visible=true`, end
  users can flip it off via the `<VisibleRulesPanel>` popover in the
  chat header. Persistence: `user_regex_preferences (user_id,
  rule_id, enabled)`. The chat-room client also keeps an in-memory
  Map so the live render flips immediately without waiting for
  revalidatePath.

`applyRegex` and `applyRegexToSegments` both respect this filter.

## Debug info

Every assistant message persists a `debugInfo` jsonb with:

```ts
{
  rawOutput: string          // raw model output (pre-applyRegex)
  systemPrompt: string       // full assembled system prompt
  matchedRules: { id, name }[]
  unmatchedRules: { id, name }[]
}
```

This is what `<DebugPanel>` renders under each AI message when the
owner-only "Debug" toggle in the chat header is ON. Owner-only ACL
on the panel; the column itself stays unfiltered so future features
(replay, regex authoring AI) can read it too.

## What's NOT live in v1

(Schema-reserved or roadmap; not deferrals from W4 anymore.)

- ReDoS pattern linter — `apply.ts` logs a >50ms warning but doesn't
  refuse the rule. v1.5 could add `redos-detector` or similar.
- Drag-to-reorder for the rule list — v1.4 ships up/down arrow
  buttons that call `swapRegexRuleOrderAction`. Drag would be a
  natural successor that reuses the same server semantics.
- Multi-rule simultaneous test in the editor — v1's test panel
  applies ONE rule (the one being edited). A "run all my rules
  against this fixture" mode is a v1.5 want.
- Component-state persistence — `host.setComponentState({state})` is
  in-memory only. v1.5 plans a `chat_sessions.component_states` jsonb
  column so iframe-mode rules can remember scroll positions etc.
- ReDoS sandbox / timeout-kill — v1 logs and keeps going; v1.5+ may
  abort.
