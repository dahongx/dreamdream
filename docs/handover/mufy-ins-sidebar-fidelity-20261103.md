# INS 侧栏来源一致性修复

2026-11-03。本地修复已验证，尚未构建／发布8091。产品记录见 [验收思考](../insights/mufy-ins-sidebar-fidelity-20261103.md)。

## 实际问题

祁述的侧栏已经集成，旧“仅本地候选”记录过时。实际来源和TEST三个页签文本完全相同；60张表情图原地址、标签、解码尺寸相同。TEST使用懒加载，正常向下滚动后从15张增加到60张，不能把未滚到的图当损坏。

进一步检查发现：来源固定位置为205px，适配器强制用了20vh；来源按钮已有8px底边距，适配器又加8px面板上边距；面板漏掉右侧10px内缩。独立iframe的按钮也没有继承Mufy宿主页提供的字体／行高重置，导致Arial／normal与来源不一致。

连续指令另有差异：来源直接追加文本，通用Host处理器在非空草稿后加换行。此前本地预览直接替换草稿，未覆盖真实聊天页的追加逻辑，无法证明连续操作正确。现预览改为复用真实的`appendComposerDraft`。

## 实现边界

- `insMusicTriggerTop`仅读取该来源包装器的数值top，支持有界px/vh/%，无匹配保留原回退。其他侧栏家族不变。
- INS面板保留来源按钮的8px底边距，额外上边距归零，右内缩10px。
- `insMusicDocumentPresentation`只为INS独立文档补来源宿主的字体、行高默认值，作者样式仍可覆盖。
- 原有`host.fillComposer(text)`默认换行契约不变；可选`{separator:'none'}`只改变草稿分隔，不增加发送、网络、存储或认证能力。宿主只接受这个固定枚举，其他值回到默认行为。
- 仅已识别的INS公开`insWrite_cen`本地化函数请求无分隔追加。其他源码字节保持原样；不改作者文案、不执行父页面注入脚本。

## 验证

- 实际来源／TEST20个独立指令均精确一致；连续第二次追加的线上失败原样保留。
- 新真实组件预览从“已有草稿”开始连续追加20个指令，每一步与实际来源精确一致；父组件重绘后同一iframe和srcdoc保留，草稿不丢，发送回调0。
- 来源390宽度面板为(120,283,260,380)。本地修复后精确相同；320和768宽度保持原宽高、205px触发位置和右内缩。320第一次切页签取样未一致，稳定态复查一致，原失败记录保留。
- 22项侧栏／追加行为回归、200断言通过；另外43项iframe／独立文档／玩家名回归、148断言通过。包含ChatRoom及相关生产依赖的范围类型检查通过。不是全脏工作区类型检查通过。
- 本地预览禁止媒体与连接请求，未启动音乐、未请求模型、未直接访问数据库。

具体证据在批次`final-acceptance/45/ins-live-followup-20261103.json`。发布候选已从实际8091源码重建为10文件；保留远程模型状态逻辑，排除未批准Bilibili安全放宽及剪贴板候选。实际TEST的几何、字体和连续拼接必须在未来受控发布后复验；目前不能标为已上线修好。
