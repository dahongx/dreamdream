# Mufy 角色卡筛选与迁移

本次实验先从本地档案筛选并确定 100 张角色卡，再选取首批 5 张验证自动化迁移与修复。所有迁移操作仅在测试服进行。

## 一 角色卡筛选

目标：从用户提供的本地角色档案中，筛出热度较高、人物资料能够对应、且测试服未已有的 100 张角色卡。

### 1 整理压缩包中的角色资料

- 输入：`prompts.by_character.jsonl.zst`。
- 解压并逐条读取，提取角色名称、别名和本地 Prompt，建立可查询的角色索引。
- 为 Prompt 保存校验指纹，核对时重新读取原文，避免角色资料串错或被意外改动。
- 输出：10,839 条本地角色档案，作为后续采集和匹配的基础。

### 2 到 Mufy 采集公开数据

按本地角色名称逐一搜索，读取完整分页，保存能够取得的收藏、点赞、对话指标、标签、公开简介和线上角色 ID。

中间遇到登录过期、浏览器暂时不可用，导致采集中断。处理方式是保存已完成进度，登录恢复后从原检查点继续，不重新采集全部角色，也不绕过认证。

最终全部 10,839 条档案完成搜索：

- 4,626 条找到线上候选，6,213 条搜索无结果。
- 得到 11,200 条本地与线上角色的关联记录，按线上 ID 去重后涉及 9,124 张卡。

这里得到的是“候选”，不是已确认匹配的角色。搜索无结果不等于角色不存在；同名搜索结果也可能属于不同人物。

### 3 按热度排序并排除已有角色

- 主排序按收藏数量从高到低；点赞和对话指标另存为独立榜单，没有混合成加权分数。
- 同一张线上卡只保留一个位置，重复采到的收藏数不相加。
- 只读核对测试服已有角色，结合名称、公开简介和人物设定指纹，排除已存在的卡片。

这一步遇到两个问题：同名角色不一定是同一张卡，测试服旧卡的来源 ID 也不完整。因此不能只靠名字防重，需要保留多项比对依据；无法可靠判断的关联不直接放行，后续执行前仍需复核旧库存防重结果。

输出：按热度排列、排除已识别的测试服已有卡后的候选清单。

### 4 核对候选是否对应本地底稿

进一步比较本地 Prompt 与 Mufy 公开开场、人物资料，检查人物、身份、关系和人生阶段是否对应。

中间发现有些同名卡实际属于不同版本。例如程今越的本地底稿是 40 岁 CEO，线上候选是 20 岁校园学生，差异不只是年龄，不能直接套用原底稿。此类错误关联排除，再从后面的热门候选补位；只调整展示样式、人物仍对应的，不因此淘汰。

另一个问题是 Mufy 公开页面无法提供隐藏 Prompt 全文，不能证明本地底稿就是线上最新版。经用户确认，改为“本地底稿加公开内容同步”的筛选口径：先确认是同一人物，能同步的公开内容后续同步，不再以无法核验隐藏全文为阻断条件。

通过依据分两类：

- 公开开场长正文与本地开场对应，忽略展示样式和空白差异。
- 开场不能直接对应时，至少两段人物事实能够对应，并满足相关身份与年龄核对要求。

输出：每张候选的确认依据或未通过原因，而不是仅凭同名判定通过。

### 5 扩大候选范围并补足 100 张

部分候选的公开资料不足以证明身份。处理方式是暂不选入、记录待确认原因，继续核对后续热门候选，不让这些卡阻塞整份名单。

建立 500 张候选池，实际读取并判定 310 张后，确定了 100 张：

| 判定结果 | 数量 | 处理方式 |
|---|---:|---|
| 开场长正文对应 | 86 | 选入 |
| 至少两段人物事实对应 | 14 | 选入 |
| 身份证据不足 | 204 | 暂不选入，保留待确认记录 |
| 本地索引名称与设定主角不一致 | 6 | 排除错误关联 |
| 尚未继续读取 | 190 | 达到 100 张后停止本轮核对 |

204 张是“证据不足”，不代表已经证明角色错误。最终 100 张是候选范围内经过身份核对、按热度优先选出的名单，不是 Mufy 全站热度前 100。

### 6 输出最终名单和核对记录

截至 2026 年 10 月 14 日，已确定 100 张角色卡。名单保留角色名称、来源链接、作者搜索快照、收藏数量、本地档案编号和确认依据，便于后续按同一份底稿执行迁移。

同时保存全量档案表、候选明细和待确认清单，便于追溯筛选过程。本阶段的结果是“名单确定”，不表示 100 张卡已经搬运完成。

### 7 筛选阶段耗时

| 环节 | 记录耗时 |
|---|---:|
| 压缩包读取与索引建立 | 约 5.85 秒 |
| 全量搜索采集 | 约 7 小时 21 分钟 |
| 身份核对的 7 轮公开资料读取 | 约 8 分 13 秒 |
| 已记录的本地排序、库存与筛选命令 | 约 1 分 3 秒 |
| 500 张候选池构建 | 约 19 秒 |

采集时间按已保存记录累计，包含网络请求和限速等待，不包含登录暂停、用户停留和开发间隔；早期失败重试未全部保留，因此不是全部请求耗时的精确总计。其他项目也是程序阶段计时，不包含全部 Agent 分析与开发，不能相加后当作完整 Agent 工时。

首次开发到全量搜索结束跨越约 17 小时 9 分钟，含开发和中断等待，不作为纯采集耗时。


## 二 角色卡迁移

确定 100 张名单后，从中选取热度优先的祁远宁、宋怀远、周岳山、薛山烬、风满楼，先验证“自动读取来源 → 转换迁入 → 校对 → 修复重跑”的完整流程。本轮仅涉及这 5 张，不代表 100 张已全部迁移。

### 第一部分 自动化迁移与修复

#### 1 准备来源并执行自动化迁移

- 将筛选结果交给迁移 Agent，绑定每张卡的线上角色 ID、本地底稿及校验指纹。
- 从正常登录的 Mufy 角色页读取公开资料、实际渲染的开场和侧栏、样式及图片音频资源，保存来源快照。
- 自动拆分本地 Prompt 的人物设定、开场、情节和输出设置等内容，映射到目标平台字段；公开开场按已确认政策同步。
- 对资源做可访问性和上传检查，对样式、播放器等做兼容转换，再写入测试服私有卡；已存在的目标卡原位更新，不重复新建。

首次严格准备检查中，5 张均未通过，主要卡在媒体缺项或样式兼容，并非重新发现 5 张人物身份都不正确。经用户确认，图片、音频无法迁入时单列后补，主体内容继续迁移；人物对应、底稿指纹和测试服写入保护仍保留。

随后处理资源上传及连接中断问题，5 张均完成测试服迁入。此时已具备主体内容、开场和可迁入资源，但不能据此认定播放器、按钮和手机排版全部合格。

#### 2 自动化如何比对

迁移前后的比对分为三层：

- **来源对应：** 核对名单中的角色 ID、来源快照 ID 和本地 Prompt 指纹，防止拿错人物或底稿。已授权的年龄元数据差异保留记录，不擅自重写人物正文。
- **内容与资源：** 检查必需设定是否成功解析、字段是否正确映射，以及图片音频取得和上传情况；缺项有明确记录，不用无关资源代替。
- **页面与交互：** 来源快照记录样式、浮层、输入框和资源状态，供目标页面对照；再检查目标页是否溢出、输入框是否被遮挡、组件是否重复、按钮操作是否真正生效。

有自动比对机制不等于这批已经完全自动验收。本轮还由 Agent 实际打开页面、点击交互、分析差异并修改通用适配规则；完整来源功能等价验收记录仍为未通过，不能写成“一次无人干预搬完”。

#### 3 迁移后如何校对

先运行程序回归检查，再分别检查 390px 手机和 1280px 桌面页面，最后对播放器、侧栏、快捷指令和展开卡片做实际操作验证。

校对不是只看截图或“已填入”提示，还检查：

- 输入框实际能否点击、值是否真正变化，是否误发消息。
- 面板能否打开和关闭，透明浮层是否遮住其他按钮。
- 可取得的音频是否加载、播放时间是否前进，缺音源是否明确不可播放。
- 手机文字是否裁切，展开和收起后页面高度是否随内容变化。

#### 4 发现的问题与修复结果

| 发现的问题 | 修复办法 | 校对结果 |
|---|---|---|
| 祁远宁、周岳山基础年龄字段与已确认底稿不同 | 按授权底稿写为 40、45 岁，保留来源差异，不改人物正文 | 字段取值已修正 |
| 部分媒体无法访问；宋怀远的部分资源超过上传限制，另有无扩展名资源识别问题 | 可识别资源按已知媒体类型处理；仍不可用或超限的单列后补，不放宽存储安全限制 | 主体迁移继续，媒体缺项仍保留 |
| 宋怀远云朵播放器依赖原站宿主，目标页留有占位 | 改为适合目标沙箱的隔离浮层，并禁用缺音源按钮 | 占位消失，只有一个实例，可展开；缺音源未伪装成可播放 |
| 新增中文文字乱码、旧组件未替换造成重复播放器 | 修正执行包编码，限定替换迁移器拥有的旧组件 | 乱码与重复实例问题已处理 |
| 薛山烬快捷指令提示已填入，但输入框实际为空 | 接入目标平台输入框桥接，恢复 18 项快捷指令 | 实测填入 271 字符，未发送消息，测试草稿已清空 |
| 薛山烬透明浮层挡住另一个面板的关闭按钮 | 设定与 MP3 共用侧栏画布，打开面板时隐藏小触发器 | 两类面板均可开关；可用音频播放时间实际前进 |
| 风满楼手机卡片文字裁切，收起后仍留大块空白 | 修正盒模型与宽度，按真实正文重新上报内嵌高度 | 内层横向溢出为 0，高度从约 11,111px 收敛到 2,328px |
| 测试服连接中断、落库成功但报告回传失败 | 先核对已有目标 ID，再续跑；批量传输并为每轮使用独立回传文件 | 避免重复建卡，写入结果与回传结果分别判断 |

上述修复已进入通用迁移器。该轮 26 项程序回归、10 个视口基础检查及所选重点交互实测通过，但仅证明当时检查项通过。随后人工复核仍发现下文所列问题，不能据此前检查宣布成品合格。

| 后续组件与交互补修 | 去除重叠后的程序时间约 18 分 16 秒 | 22 条记录，含重跑、检查及网络等待；修复上述重点交互 |

这次没有取得“首次自动化一遍迁移即合格”的完整耗时：首次检查未通过，迁入与修复交错进行。单个问题的修复时间也未独立计时，以上按修复轮次统计，不人为拆分或平均到每张卡。

#### 6 自动化程度与当前结果

- 已自动完成来源读取、内容解析和映射、资源处理、测试服写入、差异记录及规则修复后的重跑。
- 新出现的兼容问题仍需要 Agent 分析并开发通用修复，并非程序已经能无人值守解决所有新问题。
- 用户介入主要是登录、确认本地版本和媒体后补口径、提出修复要求及成品复验，没有要求用户逐字段录入或手写迁移代码；未完整统计介入次数和分钟数。
- 五卡主体均已迁入测试服，前一轮所选重点交互已修；本次人工复核又发现展示和交互差异，成品仍未验收。仍保留媒体缺项及非可移植装饰差异。记录的音频缺项分别为祁远宁 1、宋怀远 2、周岳山 1、薛山烬 5、风满楼 0 项，宋怀远另有 1 项图片缺项。
- 现有本地日志未记录本任务的模型输入、输出 Token 用量，暂不填估算值，也不将 Prompt 字符数当作 Token 消耗。

### 第二部分 人工复核与成品差距

#### 1 人工复核投入

用户对首批 5 张卡进行人工对照检查，估计平均约 **10 分钟一张，合计约 50 分钟**。这是用户提供的检查耗时估计，不是从截图时间戳或聊天间隔推算的精确计时。

检查包括演绎室预览、开始对话后的开场、展开与收起、状态栏、侧边组件及原站对应效果。这 50 分钟仅算首次检查，不含问题整理汇报、Agent 返修、返修后再次复验和媒体补齐。

#### 2 人工复核仍发现的问题

以下根据用户反馈和 19 张截图整理，均作为本轮待修项，不因前一轮程序检查通过而关闭。

| 问题类别 | 涉及角色与表现 | 当前证据及处置 |
|---|---|---|
| 顶部文案漏迁 | 风满楼缺少“我的执念，万千千千”；宋怀远缺少“市政公告 即日起……” | 原站截图能看到对应文字，用户指出此前也发生过；纳入跨卡共性检查，不能直接当作可省略装饰 |
| 开场美化丢失 | 风满楼时间地点变成普通框，出现字面 `<time>` 标签，系统提示框和“你是谁”下方样式不一致；薛山烬演绎室正确，进入对话后时间地点未美化 | 需分别核对原始文本、正则命中和两种页面渲染路径，不能只验演绎室 |
| 用户名未适配 | 薛山烬开场和状态正文仍出现 `mufyer` | 需识别用户占位来源并接入当前平台用户名；不能固定替换成某一个检查账号 |
| 状态及定制指令美化未迁入 | 薛山烬展开状态后显示分隔符、裸链接及原始文本，原站是排版卡片；底部原定制指令未保留，顶部却新增“快捷指令” | 已确认适配器删除原占位并生成顶部浮层，这是迁移引入的布局差异；后续应恢复来源位置与展示，并验证实际填入 |
| 状态栏颜色与对齐不同 | 祁远宁“安分守己”缺少原站白灰背景，黑字在暗背景上难读；周岳山同类状态栏问题，状态标题偏居中而记忆区靠左 | 核对来源背景色、文字色与对齐；不以“文字还在”认定美化通过 |
| 来源没有的侧栏出现在预览 | 祁远宁、周岳山演绎室出现原站未见的侧边快捷菜单，进入对话后又没有 | 用户反馈及侧栏截图留证；需追查来源快照、注入规则与预览组件范围，不能把新增菜单当作迁移成功 |
| 封面与布局差异 | 宋怀远原站有动态封面，目标卡封面缺失；演绎室下方卡框位置不一致，但朋友圈截图对应 | 封面缺失已记录，动态资源实际格式、映射和上传结果待查；不能凭静态截图断言平台不支持动态。朋友圈对应结果单独保留 |
| 收起后遗留占位 | 宋怀远开场展开正常，收起后仍留原展开高度的空白，演绎室和对话页均出现；对话页部分卡框位置又正常 | 用户截图及操作描述留证；需要“展开 → 收起 → 再展开”的高度回归，前一轮风满楼高度修复不能代表宋怀远已修 |

#### 3 为什么此前自动校对没有拦住
